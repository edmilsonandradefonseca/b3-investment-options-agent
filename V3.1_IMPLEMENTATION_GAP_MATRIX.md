# B3 Investment & Options Agent — V3.1 Implementation Gap Matrix

## Status

- **Architecture:** V3.1 — Frozen Integrated Architecture
- **Analytical baseline:** V2.3 — Frozen
- **Purpose:** Map the frozen V3.1 architecture to the current repository implementation before further implementation work.
- **Branch:** `feature/mcp-mvp`
- **Scope:** Architecture-to-code gap analysis; no implementation changes are authorized by this document.

> V3.1 freezes the application/service boundaries while preserving V2.3 as the analytical implementation baseline. This matrix is the implementation map for moving the current repository toward those frozen boundaries without silently changing existing analytical contracts.

---

# 1. Executive Assessment

The repository is materially stronger on the **deterministic investment-intelligence engine** side than on the **integrated application/platform** side.

### Current strengths

- Portfolio ingestion from the real BTG workbook is implemented and has passed the real-data gate.
- Option transaction ingestion and reconciliation are implemented and validated against the real portfolio.
- BRAPI stock-market adapter exists and maps data into the canonical market contract.
- OpLab option-information adapters exist.
- Quant features exist.
- Valuation engines exist for multiple methods.
- Stock and option opportunity producers exist.
- Opportunity ranking and deterministic context exist.
- Initial B3 MCP tools exist.
- Initial Obsidian MCP integration exists.
- LangGraph reasoning workflow exists as an MVP.
- Provenance, quality status and point-in-time fields are already present across important contracts.

### Main gaps

- No V3.1 B3 Orchestrator Server boundary yet.
- `b3_orchestrator()` is not yet the canonical workflow contract.
- LangGraph state is still an MVP rather than the complete V3.1 state model.
- Domain agents are mostly not yet implemented as V3.1 components.
- Insight is not yet a first-class persisted domain object with lifecycle.
- Obsidian Memory Manager is not yet implemented.
- RAG ingestion/indexing/retrieval is not yet a complete pipeline.
- Investment Committee is not yet a complete workflow component.
- Risk validation exists but is not yet integrated into the complete V3.1 decision path.
- Dashboard is not yet routed through the V3.1 server/workflow boundary.
- AI Assistant is not yet a V3.1 client of the common workflow.
- Shared identity across Portfolio / Market / Options / Obsidian / RAG / future KG needs a formal contract.
- Audit is distributed across provenance fields but does not yet exist as a complete workflow audit model.

### Architectural conclusion

The project should **not** restart its analytical implementation. The correct path is to preserve the V2.3 analytical substrate and build the V3.1 application/service boundaries around it.

# 4. P0 — Application Boundary

## 4.1 Orchestrator Contract

### Target

```python
b3_orchestrator(
    task: str,
    ticker: str | None = None,
    context: dict | None = None,
)
```

Target evolution:

```text
OrchestratorRequest
        ↓
b3_orchestrator()
        ↓
LangGraph
        ↓
OrchestratorResponse
```

### Current state

LangGraph and reasoning components exist, but the single logical V3.1 workflow contract has not yet become the canonical public/internal entry point.

### Decision

**CREATE**, not duplicate orchestration.

`b3_orchestrator()` must delegate to LangGraph rather than implement a second workflow.

---

## 4.2 B3 Orchestrator Server

### Target responsibility

- HTTP/REST
- authentication/authorization
- validation/normalization
- sessions
- security
- rate limiting
- logging/audit
- configuration/runtime
- invoke LangGraph
- return structured response

### Must not contain

- valuation logic
- portfolio strategy
- agent sequencing
- LLM reasoning
- opportunity ranking
- risk bypasses

### Current state

MCP server exists, but MCP is not equivalent to the V3.1 application server boundary.

### Action

**CREATE thin server layer.**

Recommended first implementation:

```text
FastAPI / HTTP
      ↓
request validation
      ↓
b3_orchestrator()
      ↓
response serialization
```

No investment logic in the API layer.

---

## 4.3 Typed Contracts

Create:

```text
OrchestratorRequest
OrchestratorResponse
B3State
```

These become the stable boundary between the Server and LangGraph.

The current internal dictionaries should be migrated incrementally rather than replaced in one large change.

## Gate criteria

# 31. Acceptance Criteria for V3.1 MVP

The V3.1 MVP should satisfy all of the following:

1. A client can submit a validated `OrchestratorRequest`.
2. The B3 Orchestrator Server is the service boundary.
3. Server code contains no investment workflow logic.
4. `b3_orchestrator()` is the single logical workflow contract.
5. LangGraph is the single workflow implementation.
6. Existing deterministic engines remain authoritative for calculations.
7. Portfolio context can be loaded through the controlled service/tool boundary.
8. BRAPI and OpLab retain their distinct responsibilities.
9. Opportunities converge through the canonical Opportunity model.
10. Domain agents produce structured analysis/evidence.
11. LLM use is controlled by the LLM Gate.
12. LLM provider can be changed without client/API contract changes.
13. Investment Committee produces structured human-review material.
14. Risk Validation remains downstream and deterministic.
15. Important outputs preserve provenance and PIT semantics.
16. Insights can be structured and persisted.
17. Obsidian remains the human-readable knowledge store.
18. RAG retrieval is selective and evidence-oriented.
19. No client has unrestricted access to internal resources.
20. No autonomous order execution exists.
21. Dashboard and external clients use the same logical workflow.
22. A complete golden E2E test validates the path.

# 32. Explicit Non-Goals

This matrix does **not** authorize:

- autonomous trading;
- broker order execution;
- autonomous agent loops;
- replacing deterministic calculations with LLMs;
- replacing Obsidian with a vector database;
- replacing deterministic Risk Validation with an LLM;
- implementing the full Knowledge Graph before prerequisites are stable;
- changing V2.3 analytical contracts silently;
- changing the current BRAPI/OpLab provider responsibilities.
