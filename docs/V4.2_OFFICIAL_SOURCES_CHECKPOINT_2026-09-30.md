## Gate B FD exhaustion root-cause closure — 2026-09-30

The second Ubuntu Gate B failure reproduced even after the Parquet-handle fix and with `LimitNOFILE=4096`. The failure still occurred before the first ticker completed.

Root cause was then traced to `IssuerRegistry`:

- `sqlite3.Connection` was used through its native context manager;
- SQLite's connection context manager commits or rolls back a transaction but does **not** close the connection;
- canonical Evidence normalization resolves issuer/securities for every IPE row;
- with 20 issuers and thousands of 2026 IPE rows, file descriptors accumulated until `EMFILE` (`Too many open files`) was raised while the nightly job tried to open its JSON manifest.

Corrective changes:

- `IssuerRegistry._connect()` is now an explicit context manager that always closes the SQLite connection in `finally`;
- `OfficialEvidenceBuilder` caches issuer/security relationships during one normalization run, avoiding repeated registry queries for the same issuer;
- Parquet reads remain explicitly scoped;
- pilot services remain reused across tickers;
- pilot artifacts remain implementation-versioned;
- `LimitNOFILE=4096` remains defense in depth, not the primary fix.

Validation evidence:

- synthetic test: 2,000 repeated issuer/ticker registry resolutions with no FD growth;
- synthetic test: 1,000 IPE Evidence records under a reduced NOFILE ceiling;
- complete Python suite: **559 passed**;
- frontend build: PASS;
- real CVM data were prefetched from CAD/FCA/IPE;
- with `NOFILE=128`, the real 20-stock official loader passed:
  - status: `SUCCESS`
  - requested tickers: `20`
  - resolved tickers: `20`
  - IPE documents normalized: `2,284`
  - MATERIAL: `107`
  - CANDIDATE: `551`

The temporary external-network / low-FD CI job was removed after passing, so normal CI remains independent of CVM availability.


## Live coverage pilot acceptance semantics — 2026-09-30

The first complete 20-stock Ubuntu run after the FD fix processed all 20 securities successfully from a runtime/resource perspective.

Observed live outcomes:

- 10 tickers: `MATERIAL_FOUND`, DeepSeek completed, OpenClaw completed;
- 5 tickers: `NO_MATERIAL_FOUND` with dated evidence coverage;
- 5 tickers: `COVERAGE_INSUFFICIENT` with the insufficiency preserved explicitly;
- 20/20 market evidence validated;
- 20/20 routing contracts validated;
- no FD exhaustion;
- no model failure among material dossiers.

The pilot process originally returned exit code 2 only because the implementation checkpoint incorrectly required zero `COVERAGE_INSUFFICIENT` results.

That requirement was stricter than frozen Architecture V4.2 sections 23, 33, 34.1 and 36. Architecture V4.2 explicitly defines `COVERAGE_INSUFFICIENT` as a legitimate EvidenceConclusion and requires the live coverage pilot to validate coverage states and prevent a false `NO_MATERIAL_FOUND` under insufficient coverage.

Acceptance semantics are therefore:

- `PASS`: all tickers have sufficient live coverage and no hard execution/model failure;
- `PASS_WITH_COVERAGE_GAPS`: all technical/runtime contracts pass, while one or more tickers correctly report `COVERAGE_INSUFFICIENT`;
- `LIMITED`: a real runtime, routing, market-data, official-source, provenance or model/escalation contract fails.

A `PASS_WITH_COVERAGE_GAPS` result is an acceptable V4.2 live-coverage-track outcome because it demonstrates the coverage contract rather than hiding its limitation.

## Gate C preflight false-negative closure — 2026-09-30

The first hardened Gate C retry reached the new `ollama_preflight` stage and failed in approximately 12 seconds with:

- `RuntimeError: Ollama returned empty content`.

This was not a DeepSeek reasoning failure. The preflight itself was incorrectly using a tiny inference and requiring non-empty assistant content.

Ollama's documented model-preload contract explicitly uses an empty chat request:

- `POST /api/chat`;
- configured model;
- `messages: []`;
- optional `keep_alive`.

A successful preload is expected to return an empty assistant content value and a completed load response. Therefore requiring non-empty content in preflight was a false-negative condition.

Corrective changes:

- preflight no longer performs any reasoning inference;
- preflight queries `/api/version`;
- verifies the configured model through `/api/tags`;
- records models already resident through `/api/ps`;
- preloads the model with an empty `/api/chat` request and `keep_alive=5m`;
- requires the preload response to complete;
- verifies the requested model is resident in `/api/ps` afterward;
- normal historical DeepSeek reasoning remains unchanged after preflight;
- standalone production-host preflight scripts were added:
  - `scripts/validate_v42_ollama_runtime.py`
  - `scripts/run_v42_ollama_preflight.sh`

Validation after this correction:

- CI #1093: PASS;
- Python suite: `574 passed`;
- frontend build: PASS.

The next production test is intentionally two-stage:

1. short isolated Ollama preflight;
2. only if preflight passes, execute Gate C replay.
