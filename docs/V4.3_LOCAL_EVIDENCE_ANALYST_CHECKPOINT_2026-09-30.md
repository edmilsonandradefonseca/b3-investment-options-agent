# V4.3 Local Evidence Analyst — Implementation Checkpoint — 2026-09-30

## Objective

Implement the V4.3 decision that DeepSeek R1 8B is an asynchronous local Evidence analyst, not a mandatory hop before OpenClaw/Luna.

## Architectural source

- `docs/ARCHITECTURE_V4.3.md`

V4.3 is additive on top of V4.0–V4.2.

## Implemented behavior

### 1. Production nightly path is asynchronous by default

`NightlyIntelligenceJob` now defaults to:

```text
local_analysis_mode = enqueue
```

For MATERIAL evidence:

```text
acquire/normalize/materiality
        ->
persist research result
        ->
enqueue local Evidence analysis
        ->
return without calling DeepSeek
```

The legacy `inline` mode remains available only for V4.2 component/pilot compatibility.

### 2. Local analysis queue

Implemented in:

- `src/b3_agent/intelligence/local_evidence_analysis.py`

Properties:

- deterministic Evidence fingerprint;
- deterministic analysis ID;
- idempotent enqueue;
- queue lifecycle:
  - `PENDING`
  - `RUNNING`
  - `READY`
  - `DEGRADED`
  - `FAILED`
- failed analyses may be retried;
- changed Evidence creates a different fingerprint/request.

Filesystem layout:

```text
data/derived/local_evidence_analyst/
    queue/
    runs/
    latest/
    manifests/
```

All content is derived/rebuildable.

### 3. Local worker

Implemented in:

- `src/b3_agent/jobs/local_evidence_analyst.py`
- `scripts/run_local_evidence_analyst.py`
- `scripts/run_local_evidence_analyst.sh`

The worker:

- consumes queued requests sequentially;
- calls local Ollama/DeepSeek only in the worker;
- requests a runtime-enforced JSON Schema via Ollama structured outputs;
- persists the dossier;
- records READY/DEGRADED/FAILED;
- records queue manifest and remaining backlog.

### 4. Dossier quality gate

A dossier is not reusable by senior reasoning when it is degraded.

Implemented quality flags include:

- `INVALID_JSON`
- `INVALID_SCHEMA`
- `OUTPUT_LIMIT_REACHED`
- `MISSING_CONTENT`
- `UNKNOWN_EVIDENCE_REF`
- `MODEL_FAILURE`

The observed V4.2 failure mode where DeepSeek hit `num_predict` is therefore explicitly detected and prevented from contaminating senior context.

The local dossier contract is now `b3_local_evidence_analyst_v2`. V2 uses Ollama structured outputs with a JSON Schema at the API boundary, while preserving post-response schema/reference validation as defense in depth.

### 5. Nonblocking senior context

Implemented in:

- `src/b3_agent/intelligence/senior_context.py`

OpenClaw/Luna context assembly:

- always includes canonical Evidence;
- reads a local dossier only if one already exists;
- never waits for local inference;
- includes the dossier only when:
  - status is READY;
  - Evidence fingerprint matches;
  - no quality flags exist;
  - the dossier is not stale.

Missing, pending, failed, degraded or stale local analysis is omitted.

The senior boundary itself was also extended:

- `AgentContext.derived_intelligence` is separate from deterministic facts and canonical Evidence;
- the orchestration state can carry optional `derived_intelligence`;
- specialist, synthesis and investment-reasoning agents receive it explicitly as non-authoritative context;
- local dossiers never enter `deterministic_context`.

### 6. Scheduler separation

Updated:

- `scripts/install_nightly_intelligence_timer.sh`

Operational sequence:

```text
22:00  b3-nightly-intelligence
       acquire + normalize + materiality + enqueue

22:15  b3-local-evidence-analyst
       consume up to 5 queued local analyses
```

The local worker uses lower runtime priority than acquisition:

- `Nice=15`;
- `CPUWeight=10`;
- best-effort IO priority.

### 7. V4.2 compatibility

Historical V4.2 pilot scripts explicitly request:

```text
local_analysis_mode = inline
```

This keeps prior acceptance tooling reproducible while production behavior moves to V4.3.

## Shared-host arbitration

V4.3 keeps the requirement for one heavy local reasoning job at a time per host.

B3 now isolates local reasoning into a separate worker, which is the prerequisite for a shared B3/João host-level lock. The cross-project lock itself is not introduced in this branch because João must participate in the same lock contract; adding a B3-only lock would not provide real cross-project arbitration.
